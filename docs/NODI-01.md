# NODI-01: Разработка кроссплатформенного CLI для инженерных проектов

## 1. Цель

Разработать **Nodi CLI v0.1**, минималистичную утилиту для публикации, хранения и получения инженерных файлов между компьютерами.

Главный сценарий использования:

1. Я создаю CAD-проект на домашнем Windows-ПК или MacBook.
2. Публикую его производственные файлы в приватном облачном хранилище.
3. На другом компьютере открываю терминал.
4. Выполняю `nodi get macstand`.
5. Получаю нужные файлы в отдельной папке на рабочем столе.

Утилита должна работать независимо от установленного CAD-программного обеспечения.

**Никаких VPN, Tailscale, сетевых папок или постоянно работающего домашнего сервера.**

## 2. Технологический стек

- Язык: Go.
- Поддерживаемые платформы: Windows amd64, macOS arm64.
- Желательно дополнительно поддержать macOS amd64.
- Хранилище: приватный GitHub-репозиторий и GitHub Releases.
- Передача: HTTPS через GitHub API.
- Метаданные: JSON.
- Архивы: ZIP.
- Контроль целостности: SHA-256.
- Авторизация: GitHub token с минимально необходимыми правами.
- Тестирование: стандартный Go testing.
- Сборка: Go build и GitHub Actions.

Используй стандартную библиотеку Go везде, где это разумно.

Не добавляй базу данных, веб-сервер, Docker, веб-интерфейс или микросервисы.

## 3. Архитектура

Разделить три логические функции:

**Storage:** работа с GitHub Releases, манифестами, версиями и архивами.

**CLI:** пользовательские команды, аргументы и вывод информации.

**Local:** скачивание, распаковка, проверка целостности и управление локальными файлами.

Не требуется превращать их в отдельные сервисы.

Архитектура должна позволять в будущем заменить GitHub на другое хранилище без переписывания пользовательских команд.

## 4. Команды

### `nodi version`

Показать версию CLI, платформу и архитектуру.

### `nodi list`

Вывести опубликованные проекты:

- Название.
- Последнюю доступную версию.
- Краткое описание.
- Статус.

По умолчанию показывать только released-проекты.

### `nodi info macstand`

Показать:

- Название проекта.
- Описание.
- Доступные версии.
- Форматы файлов.
- Размер пакета.
- Дату публикации.
- Дополнительные метаданные, если они заданы.

### `nodi get macstand`

Скачать последнюю опубликованную версию проекта.

По умолчанию сохранять в:

Windows: `Desktop\Nodi\macstand\<version>\`

macOS: `~/Desktop/Nodi/macstand/<version>/`

Реальный путь к Desktop определять с учётом ОС и пользовательских настроек, с возможностью явно указать другую директорию.

Поддержать:

`nodi get macstand --version 1.0.0`

`nodi get macstand --output <path>`

Повторная загрузка той же версии не должна молча перезаписывать существующие файлы.

### `nodi publish macstand <directory>`

Опубликовать проект из указанной локальной директории.

Например:

`nodi publish macstand ./manufacturing --version 1.0.0`

Алгоритм:

1. Проверить существование директории.
2. Просканировать включаемые файлы.
3. Сформировать манифест проекта.
4. Рассчитать контрольные суммы SHA-256.
5. Создать ZIP-архив.
6. Загрузить его в приватное хранилище.
7. Создать опубликованную версию.
8. Сообщить результат.

Не перезаписывать уже опубликованную версию.

Не публиковать проект без явной команды пользователя.

Для публикации требовать указания версии.

### `nodi open macstand`

Открыть локальную директорию последней скачанной версии проекта системным файловым менеджером.

### `nodi help`

Показать команды и краткие примеры.

## 5. Организация хранения на GitHub

GitHub Releases использовать как хранилище **производственных пакетов**, а не исходного кода CAD-проектов.

Предложи простую схему идентификации проектов и версий, например:

`macstand/v1.0.0`

Однако проверь фактические ограничения тегов, Releases и API GitHub. Не предполагай, что GitHub предоставляет готовую структуру каталогов проектов.

Реализуй индексирование на основании согласованного формата тегов и метаданных.

Каждая версия содержит:

- ZIP с файлами.
- JSON-манифест.
- Список файлов и их SHA-256.
- Название и версию проекта.
- Дату публикации.
- Необязательное описание.

Предусмотреть статусы `draft` и `released`, но **MVP не должен автоматически считать черновые CAD-файлы готовыми для производства**.

Для GitHub Releases используй реальные механизмы draft/prerelease и явно определённые метаданные Nodi.

Не использовать prerelease как единственный признак технологической готовности.

## 6. Безопасность и авторизация

Хранилище должно быть приватным.

Реализуй:

- Настройку GitHub-авторизации.
- Раздельные права чтения и публикации.
- HTTPS.
- Проверку SHA-256 после загрузки.
- Ограничения размера архивов.
- Защиту от Zip Slip и выхода путей за целевую директорию.
- Запрет небезопасных абсолютных путей и символьных ссылок в архивах.
- Отказ от молчаливой перезаписи файлов.
- Понятные сообщения об ошибках.

Токены не должны попадать в репозиторий, логи или экспортируемые архивы.

Предпочти системное безопасное хранилище учётных данных. Для MVP допустим ввод токена через стандартный ввод без его отображения и использование прав доступа к конфигурации текущего пользователя.

Не передавай токены через аргументы командной строки.

На компьютерах, которым нужен только `get`, использовать доступ исключительно на чтение.

## 7. Установка

Пользователь не должен устанавливать Go, Node.js, Python или Git.

Подготовить самостоятельные сборки:

- `nodi-windows-amd64.exe`
- `nodi-darwin-arm64`
- `nodi-darwin-amd64`, если возможно.

**Установка должна выполняться через терминал.**

Для Windows подготовить PowerShell-установщик, который:

1. Получает совместимую сборку из доверенного релиза.
2. Проверяет контрольную сумму.
3. Размещает программу в пользовательской директории.
4. Добавляет её в пользовательский PATH.
5. Проверяет `nodi version`.

Для macOS подготовить аналогичный установщик для Terminal/zsh.

Не требовать прав администратора без необходимости.

Не отключать системные защитные механизмы ради установки.

Подготовить возможность в будущем распространять Nodi через Homebrew и winget. Публикация в эти каталоги не обязательна для v0.1.

Исходный код установщиков должен быть доступен для просмотра до выполнения.

## 8. Сборка и тестирование

Создать автоматические тесты:

- Разбор команд.
- Валидация названий проектов и версий.
- Формирование и чтение манифеста.
- Создание ZIP.
- Распаковка.
- Проверка SHA-256.
- Повторное скачивание.
- Защита от опасных путей.
- Обработка ошибок сети.
- Обработка недоступного проекта.
- Работа с тестовым GitHub API.

Использовать HTTP-mock и временные директории, чтобы большинство тестов выполнялось без обращения к реальному GitHub.

Создать GitHub Actions workflow для проверки и кроссплатформенной сборки.

Сборки должны быть воспроизводимыми насколько это возможно в рамках выбранной технологии.

## 9. Реальная демонстрация

Создать небольшой тестовый инженерный проект с несколькими фиктивными DXF и PDF-файлами.

Проверить полный сценарий:

1. Подготовить тестовый пакет.
2. Опубликовать его в тестовом приватном репозитории.
3. Получить список проектов.
4. Посмотреть информацию.
5. Скачать конкретную версию.
6. Проверить контрольные суммы.
7. Открыть локальную директорию.
8. Повторить скачивание и проверить отсутствие нежелательной перезаписи.

Если реальные GitHub credentials или репозиторий недоступны, не выдумывать их и не утверждать успешное end-to-end тестирование. Выполнить локальный интеграционный сценарий на mock-сервере и обозначить, что осталось проверить вручную.

Не загружать реальные производственные файлы без моего разрешения.

## 10. Организация проекта

Создать отдельный репозиторий `nodi`.

Предлагаемая структура:

```text
nodi/
  cmd/
    nodi/
  internal/
    cli/
    storage/
    archive/
    config/
  scripts/
    install-windows.ps1
    install-macos.sh
  .github/
    workflows/
  docs/
  README.md
  go.mod
```

Допускается упростить структуру, если для MVP она избыточна.

README должен содержать:

- Назначение Nodi.
- Инструкцию установки для Windows и macOS.
- Первую настройку GitHub.
- Примеры всех команд.
- Публикацию проекта.
- Загрузку проекта.
- Обновление и удаление CLI.
- Ограничения первой версии.

## 11. Ограничения проекта

**Нельзя:**

- Создавать веб-интерфейс.
- Писать собственный облачный backend.
- Добавлять базу данных.
- Реализовывать синхронизацию в фоне.
- Использовать Tailscale.
- Управлять CypCut.
- Автоматически отправлять задания на лазер.
- Делать сложную систему ролей пользователей.
- Переусложнять архитектуру дополнительными абстракциями.

Nodi должен быть обычным CLI, который работает по запросу пользователя.

Использование на компьютере предприятия возможно только с разрешения ответственных за оборудование и информационную безопасность.

## 12. Критерий завершения

Работа считается завершённой, когда:

- Nodi собирается под Windows и macOS ARM64.
- Устанавливается через терминал без установленного Go.
- Команды `list`, `info`, `get`, `publish`, `open`, `version` работают.
- Файлы передаются через HTTPS.
- Приватные проекты требуют авторизации.
- Версии не перезаписываются случайно.
- ZIP проверяются и безопасно распаковываются.
- Есть автоматические тесты.
- Есть инструкция установки и использования.
- Проведено реальное или явно обозначенное mock end-to-end тестирование.

**В конце выдай короткий отчёт:** что реализовано, результаты тестов, путь к проекту, команды установки, ограничения.

Работай автономно. Не останавливайся ради мелких архитектурных вопросов. Не создавай дополнительные этапы NODI-02 и NODI-03.

Мне нужна первая работающая версия Nodi, которой можно начать пользоваться на собственных Windows-ПК и MacBook.

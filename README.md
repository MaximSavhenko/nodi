# Nodi CLI 0.4

Nodi передаёт файлы и их версии между Windows и macOS через приватный репозиторий GitHub и его Releases. На компьютере получателя нужны только Nodi и доступ в интернет. CAD, Git, Go, VPN и домашний сервер не нужны.

Команды запускаются вручную. Nodi не проверяет технологическую пригодность чертежей: `released` означает доступность пакета для скачивания.

В 0.4.0 доступны команды NODI-06:

При очистке NODI-07 обнаружено, что 0.4.0 безопасно останавливает удаление draft, если GitHub не возвращает его через поиск Release по тегу. Release и tag остаются, tombstone может быть уже сохранён. Исправление подготовлено в кандидате 0.4.1: проверка использует согласованный release ID, а перед удалением tag проверяет весь список Releases, включая draft. Опубликованные релизы 0.4.0 и более ранних версий остаются неизменными. Кандидат 0.4.1 ещё не опубликован.

```text
nodi send DXF --dry-run
nodi send DXF --name macstand-dxf
nodi delete PROJECT --version 0.1.0 --dry-run
nodi delete PROJECT --all --dry-run
nodi update --check
```

Вложенная папка отправляется независимо от привязанного родителя. Отдельный файл из привязанного проекта нельзя отправить вместо целого пакета. `--name` не переименовывает существующую привязку. Для непривязанного source первая отправка сохраняет имя в глобальной конфигурации (`sent/`), не в source; повторные отправки используют это имя. Если имя уже занято и локальной записи нет, выберите другое через `--name`. Для собственного старого пакета явно выполните `nodi init PROJECT` в его полной папке. После переносов папки или на другом компьютере владение автоматически не предполагается.

`send --dry-run` не создаёт ZIP, привязку, локальную запись или remote object: показывает файлы/размер/SHA-256, исключения и только проверенную remote версию. Исключённые каталоги показываются целиком с причиной, их содержимое не читается. Без write credential или GitHub версия обозначается NOT VERIFIED. Все выбранные файлы перепроверяются при реальной отправке.

Удаление требует отдельного write credential и реального доступа Contents write. После точного списка `--version` требует ввод имени проекта, `--all` — `DELETE ALL PROJECT`. Маски и удаление без одного из этих флагов запрещены. Dry-run выполняет только GET и не проверяет write capability. Проверяются manifest, размер и SHA-256 архива, tag identity и снимок непосредственно перед удалением. Неизвестные assets, повреждённые packages и отсутствующие tags блокируют операцию. Release удаляется первым, tag — после API-проверки его отсутствия; частичный сбой явно сообщает состояние и останавливает продолжение. Локальные downloads сохраняются. Completion cache текущего компьютера очищается; на других компьютерах действует обычное обновление через 60 секунд, offline cache может быть устаревшим.

Удалённые номера сохраняются в постоянных refs `nodi-deleted/PROJECT/vVERSION`. Их нельзя удалять вручную: новая отправка считает их использованными. Старые schema-1 packages остаются читаемыми. **Перед удалением обновите все компьютеры, которые отправляют пакеты:** Nodi 0.3.0 не знает эту историю, поэтому после удаления прежний writer может повторно занять номер. Получатели 0.3.0 могут продолжать скачивать оставшиеся packages. Не используйте старый writer в очищенном namespace.

`update --check` читает последний стабильный релиз публичного CLI repository, показывает установленную версию и не обновляет программу. Разделение provider и CLI описано в [архитектуре](docs/ARCHITECTURE.md); проверки NODI-06 — в [отчёте](docs/NODI-06-STATUS.md).

## GitHub и пакетные менеджеры

- [nodi](https://github.com/MaximSavhenko/nodi) — публичный исходный код (MIT), проверки и бинарные релизы.
- [homebrew-nodi](https://github.com/MaximSavhenko/homebrew-nodi) — публичный Homebrew tap.
- [nodi-packages](https://github.com/MaximSavhenko/nodi-packages) — приватное хранилище пакетов; требуется доступ пользователя.

Версия [0.4.0](https://github.com/MaximSavhenko/nodi/releases/tag/v0.4.0) завершает NODI-06, сохраняя постоянный Tab completion и передачу `send PATH` → `get PROJECT` с проверкой SHA-256. Публикация стабильного CLI разрешена только после native CI для Windows amd64 и macOS ARM64/Intel и проверки обновления с 0.3.0. Физическая приёмка на устройствах пользователя остаётся отдельным шагом. [Winget PR 0.1.0 #450627](https://github.com/microsoft/winget-pkgs/pull/450627) сохранён; manifests 0.4.0 подготовлены отдельно и не заменяют существующий PR или подтверждение Microsoft.

macOS, Apple Silicon и Intel:

```sh
brew install MaximSavhenko/nodi/nodi
nodi version
nodi help
brew update
brew upgrade MaximSavhenko/nodi/nodi
brew uninstall MaximSavhenko/nodi/nodi
```

Formula устанавливает готовый бинарник из ZIP с проверкой SHA-256; Go для установки не нужен. Tap автоматически обновляется каждый час только из стабильного релиза с подтверждающим `validation.json`. Homebrew должен быть установлен отдельно.

Windows, **после принятия пакета в официальный источник winget**:

```powershell
winget install --id MaximSavhenko.Nodi --exact --source winget
nodi version
nodi help
winget upgrade --id MaximSavhenko.Nodi --exact --source winget
winget uninstall --id MaximSavhenko.Nodi --exact
```

WinGet управляет portable ZIP, командой `nodi` в PATH, установленной версией и удалением. Пока пакет не находится в официальном источнике, используйте терминальный установщик ниже. Локальная проверка manifest и установка из manifest не означают доступность пакета в каталоге Microsoft. Актуальные результаты: [NODI-03](docs/NODI-03-STATUS.md); история первого выпуска: [NODI-02](docs/NODI-02-STATUS.md).

При переходе с терминального установщика на winget удалите прежний `%LOCALAPPDATA%\Nodi\bin\nodi.exe` и его запись пользовательского PATH по инструкции удаления ниже. Затем установите пакет через winget и откройте новый терминал. Так обновления winget будут запускать управляемый им бинарник; скачанные проекты и конфигурация сохранятся.

## Повседневная работа

В 0.3.0 обычная отправка сразу создаёт доступную версию, без браузера, черновика и ручных подтверждений. Первичная настройка доступа и согласие на изменение shell-профиля выполняются отдельно. Диагностика исправления: [FILE-DELIVERY](docs/FILE-DELIVERY.md); выпуск и приёмка: [NODI-05](docs/NODI-05-STATUS.md).

Один раз настройте доступ к приватному хранилищу. На Windows-отправителе используйте отдельный токен с Contents write:

```sh
nodi setup --repo MaximSavhenko/nodi-packages --write
```

На Mac-получателе используйте отдельный токен с Contents read:

```sh
nodi setup --repo MaximSavhenko/nodi-packages
```

Токен вводится скрыто и сохраняется в существующем защищённом read/write слоте. Повторный setup проверяет сохранённые credentials. Обычные send/list/get не запрашивают токен. `setup --check` выполняет только GET-запросы и не записывает настройки. Обычный setup проверяет права записи заведомо недопустимым Git ref: GitHub отклоняет его, объект не создаётся. Слот read с правами записи отмечается отдельно; для получателя выдайте минимальный Contents read. При смене сохранённого хранилища требуется подтверждение; setup не изменяет привязки проектов.

Повседневная передача:

```powershell
nodi send "C:\CAD\MacStand"
```

```sh
nodi list
nodi get macstand
nodi get macstand --version 0.1.0
```

`send` принимает файл или каталог. Имя — basename каталога или имя файла без расширения: lowercase, пробелы/разделители становятся дефисами, кириллица транслитерируется. Для необычных/длинных имён используется стабильный SHA-256 суффикс. Например, `MacStand` → `macstand`, `Макет с пробелами` → `maket-s-probelami`. Отправка не создаёт `.nodi` и не изменяет источник. При наличии точной привязки каталога сохраняются её project/repository/metadata. Частичная отправка файла или вложенного каталога привязанного проекта отклоняется, чтобы не заменить состав пакета.

Для уже привязанного проекта достаточно `nodi publish` из его папки или вложенной папки. Обычная публикация сразу создаёт released-пакет без интерактивных подтверждений. `nodi publish --draft` явно создаёт недоступный для get черновик. Старый явный синтаксис с project/path/version/status сохраняется.

Первая версия — 0.1.0, затем PATCH; `publish --minor` и `publish --major` увеличивают соответствующую часть. Учитываются GitHub версии, drafts и reserved tags; локальный last_version не управляет версионированием. Неизменённый released-пакет не создаёт новую версию. Для неизменённого draft обычная публикация создаёт следующую released-версию, сохраняя старый draft. Изменение времени файла не считается изменением; description/metadata без изменения файлов и статуса не создают новую версию.

Перед загрузкой повторно проверяются файлы, привязка и удалённое состояние. Git ref резервируется атомарно; конфликт прекращает публикацию. Новый релиз сначала закрыт как draft. После загрузки Nodi повторно скачивает manifest и ZIP, проверяет все поля, размер и SHA-256. Затем устанавливает released-статус и ещё раз читает релиз по тегу и его assets; только после этого сообщает успех. Незавершённый draft/tag сохраняется для диагностики; автоматического удаления, перезаписи или retry нет.

`status` остаётся только чтением и показывает Added/Modified/Deleted по SHA-256. При отсутствии связи/credentials — NOT VERIFIED. Read credentials сравнивают только released-версии. `init` сохраняет schema 1 и не меняет существующую привязку.

## Tab completion и версия

```sh
nodi -v
nodi --version
nodi completion
nodi setup --completion --check
nodi setup --completion
```

`version`, `-v` и `--version` показывают реальную версию бинарника и платформу. `completion` выводит инструкции; с именем оболочки — только скрипт. Подсказываются команды, auth login/logout, флаги, draft/released, проекты, версии для --version и пути для publish/--output/--metadata. Проекты и версии берутся через GitHub API с кешем на 60 секунд, привязанным к repository, роли и fingerprint credentials. Для publish используются write credentials и видны drafts; get использует read credentials и только выпущенные версии.

Включить **только в текущем терминале**, без изменения shell profiles:

```zsh
autoload -Uz compinit; compinit
source <(nodi completion zsh)
```

```bash
source <(nodi completion bash)
```

```powershell
nodi completion powershell | Out-String | Invoke-Expression
```

Homebrew автоматически устанавливает `_nodi` и bash completion в стандартные каталоги. Если оболочка уже использует `brew shellenv` и compinit/bash-completion, Tab доступен после открытия нового терминала. Для zsh `brew shellenv` должен выполняться до compinit; настройка зависит от существующего shell framework. [Инструкция Homebrew](https://docs.brew.sh/Shell-Completion).

Для постоянного подключения один раз выполните `nodi setup --completion` и подтвердите показанные изменения. Windows-установщик предлагает эту настройку после установки. На Windows добавляется один блок в `$PROFILE.CurrentUserAllHosts` отдельно для PowerShell 5.1 (`Documents/WindowsPowerShell/profile.ps1`) и 7 (`Documents/PowerShell/profile.ps1`), включая перенаправленный Documents. На macOS используется `.zshrc` в экспортированном `ZDOTDIR` или домашней папке. Существующие настройки, BOM и UTF-16 сохраняются; перед добавлением в существующий файл создаётся резервная копия `*.nodi-backup-*`. Повторный setup/обновление не добавляет второй блок. Отказ или пустой ввод ничего не меняет. Отредактированные/неполные блоки, неизвестная кодировка и symlink-профили требуют ручной проверки.

`nodi setup --completion --check` только читает конфигурацию: не создаёт файлы/каталоги, не запрашивает согласия и не исполняет пользовательские профили. `CONFIGURED` означает наличие управляемого блока; распознанная ручная настройка или Homebrew initialization отмечается отдельно. Это статическая диагностика, а не доказательство работы произвольного shell framework. После настройки откройте **новый терминал** и проверьте `nodi get nod<Tab>` и `nodi get PROJECT --version <Tab>`. Ошибки синтаксиса профиля, поздняя перезапись completion и ограничения ExecutionPolicy могут помешать загрузке; Nodi не меняет политику выполнения.

На macOS `setup` предпочитает установленный Homebrew `_nodi` из `$(brew --prefix)/share/zsh/site-functions`, поддерживая `/opt/homebrew` (Apple Silicon) и `/usr/local` (Intel). Если штатные `brew shellenv` и `compinit` уже настроены, правка `.zshrc` не предлагается. Иначе, только с согласия, добавляется Homebrew fpath и регистрация `_nodi`, в том числе после уже инициализированного framework. Для самостоятельного бинарника используется существующая команда `nodi completion zsh`. Путь установки подхватывается в новой сессии, если `nodi` ещё отсутствует в PATH.

Winget ZIP содержит completion scripts, а встроенная команда работает и при установке одного exe. Portable winget не запускает post-install scripts: после установки выполните `nodi setup --completion` один раз. Для bash сохраняется ручное подключение через `~/.bashrc`.

Tab не запрашивает токен и не раскрывает credentials. Общий сетевой таймаут 1,5 секунды. При сетевом сбое используется доступный кеш, без кеша — пустой результат. Подсказки из кеша могут быть устаревшими и не заменяют проверку перед publish/get. При смене repository, роли или токена чужой кеш не используется. Ошибки completion подавляются; терминал продолжает работу.

## Установка через терминал

В этой локальной поставке самостоятельные программы находятся в `dist/`:

- `nodi-windows-amd64.exe` — Windows x64.
- `nodi-darwin-arm64` — Apple Silicon.
- `nodi-darwin-amd64` — Intel Mac.
- `SHA256SUMS` — контрольные суммы трёх программ и трёх ZIP-пакетов.

Сначала прочитайте исходный код установщика. Go нужен разработчику для сборки, но не пользователю для установки и работы.

**Windows, PowerShell:**

```powershell
cd C:\projects\nodi
Get-Content .\scripts\install-windows.ps1
.\scripts\install-windows.ps1 -BundleDirectory .\dist
nodi version
```

Установка: `%LOCALAPPDATA%\Nodi\bin\nodi.exe`, пользовательский PATH. Установщик проверяет SHA-256, запускает `version` и предлагает `setup --completion`, который спрашивает согласие отдельно для каждого профиля. `-NoCompletion` пропускает этот шаг. Установка старых релизов без `setup` поддерживается. Если команда не появилась в другом терминале, откройте его заново. Администратор не нужен. При запрете выполнения скриптов вашей организацией используйте разрешённый организацией способ; установщик не изменяет ExecutionPolicy.

**macOS, Terminal/zsh:** скопируйте `dist/` и `scripts/install-macos.sh` на Mac, сохранив структуру папок.

```sh
cat scripts/install-macos.sh
sh scripts/install-macos.sh --bundle ./dist
export PATH="$HOME/.local/bin:$PATH"
nodi version
```

Установка: `~/.local/bin/nodi`. В интерактивном терминале установщик предлагает `setup --completion`; изменение `.zshrc` требует отдельного согласия. Без терминального stdin выполняется только `setup --completion --check` и выводится инструкция; `--no-completion` пропускает этот шаг. Для текущего терминала используйте `export PATH` выше. Явный `--add-path` по-прежнему разрешает добавление PATH в `~/.zprofile`. На Mac применяются обычные правила Gatekeeper; установщик не снимает quarantine, не отключает защиту и не подписывает программу.

Установка или обновление до версии 0.4.0:

```powershell
.\scripts\install-windows.ps1 -Repository MaximSavhenko/nodi -Release v0.4.0
```

```sh
sh scripts/install-macos.sh --repo MaximSavhenko/nodi --release v0.4.0
```

Windows поддерживает приватный релиз CLI через переменную `NODI_INSTALL_TOKEN`; macOS сетевой режим рассчитан на публичный доверенный релиз, для приватной поставки используйте локальный комплект. Токены никогда не передаются аргументом команды. Контрольная сумма из того же доверенного релиза проверяет целостность; отдельной криптографической подписи поставки в v0.1 нет.

## Первая настройка GitHub

1. Используйте подготовленный **private** репозиторий `MaximSavhenko/nodi-packages` с начальным коммитом/README, либо свой отдельный приватный репозиторий. Исходный код Nodi храните отдельно. Nodi не создаёт облачные репозитории автоматически и отказывается работать с публичным хранилищем.
2. Создайте fine-grained Personal Access Token только для выбранного репозитория. Для получения: **Contents: Read-only**. Для публикации на домашнем компьютере: отдельный токен **Contents: Read and write**. Стандартное право Metadata оставьте включённым. При необходимости подтвердите доступ организации/SSO. Не выдавайте права на остальные репозитории.
3. Выполните настройку на каждом компьютере:

```text
nodi config --repo MaximSavhenko/nodi-packages
nodi auth login
```

Вставьте токен в скрытый ввод и нажмите Enter. На компьютере автора отдельно:

```text
nodi auth login --write
```

Windows хранит токены в виде DPAPI-данных, привязанных к текущему пользователю. На macOS MVP использует файл с правами `0600` в каталоге `0700`, а не Keychain. Конфигурация без токенов: Windows `%APPDATA%\nodi`, macOS `~/Library/Application Support/nodi`. Не выбирайте для конфигурации общий или синхронизируемый каталог.

Альтернатива для CI/временной сессии: `NODI_REPO`, `NODI_READ_TOKEN`, `NODI_WRITE_TOKEN`. Переменная `NODI_CONFIG_DIR` задаёт отдельный каталог конфигурации и локальных записей. Не записывайте токены в исходники, команды с литералами токенов, `.env` проекта или логи. Read-токен не заменяется автоматически write-токеном. Удаление сохранённых данных: `nodi auth logout`; токены в переменных окружения удаляются отдельно, отзыв прав выполняется на GitHub.

GitHub применяет реальные права токена. Выбор `--write` определяет слот хранения и не увеличивает права. GitHub предоставляет черновики только пользователям с правом push; для `list --all` и `info --all` Nodi использует write-токен. [Документация Releases API](https://docs.github.com/en/rest/releases/releases).

## Команды

```text
nodi version
nodi help
nodi list
nodi list --all
nodi info macstand
nodi info macstand --all
nodi get macstand
nodi get macstand --version 1.0.0
nodi get macstand --output "D:\Engineering\macstand-1.0.0"
nodi open macstand
```

`list` показывает последнюю по числовой версии запись для каждого проекта; `info` — все доступные версии, описание, форматы, размер ZIP, дату подготовки публикации и дополнительные метаданные. Релизы стороннего формата игнорируются. Список GitHub читается постранично. Проект: латинская строчная буква, затем строчные буквы/цифры/дефисы, до 63 символов; системные имена Windows запрещены. Версия: `MAJOR.MINOR.PATCH`, без `v`, ведущих нулей и prerelease-суффиксов. `1.10.0` новее `1.9.0`.

`get` без версии выбирает максимальную выпущенную версию. По умолчанию папка — `Desktop/Nodi/PROJECT/VERSION`. Windows Desktop определяется через Known Folder API, включая перенаправление в OneDrive; macOS — `~/Desktop`, включая стандартный iCloud Desktop. `--output` — **точная новая папка результата**, без добавления проекта/версии. Любой существующий путь, включая пустую папку, отклоняется. Для второй копии выберите другой путь. `open` открывает последнюю по времени успешно скачанную и ещё существующую папку данного проекта, в том числе при использовании `--output`, без обращения к сети.

## Публикация

Подготовьте отдельную папку доставки. Включаются обычные файлы любых форматов и вложенные каталоги; пустые каталоги не передаются. Символические ссылки, специальные файлы и непереносимые имена отклоняются.

Исключаются скрытые имена (включая .nodi/.git/.env/.ssh/.aws), имена с credential/secret, token./-token/_token, password, id_rsa/id_ed25519/id_ecdsa; config.json/auth.json/token/tokens.json; расширения .credential/.pem/.key/.p12/.pfx/.keystore/.kdbx/.log/.tmp/.bak; node_modules/__pycache__/venv/env/build/dist/target/coverage/logs; Thumbs.db и desktop.ini. Каталог текущей Nodi-конфигурации исключается независимо от имени. Политика действует и при отправке отдельного файла: секретный или служебный источник отклоняется.

Это фильтр имён, не анализ содержимого. Он не распознаёт секрет, спрятанный в обычном документе. Выбирайте подготовленную папку доставки; расширения .key или каталоги build могут исключить и полезные файлы. Не меняйте имя секретного файла ради обхода фильтра. Состав пакета виден после получения через info/manifest.

По умолчанию пакет выпущен. Для черновика используйте --draft или совместимый --status draft:

```text
nodi publish macstand ./manufacturing --version 0.1.0 --status draft
```

Для сознательно выпущенного пакета:

```text
nodi publish macstand ./manufacturing --version 1.0.0 --status released --description "Подставка, комплект экспортов"
nodi publish macstand ./manufacturing --version 1.0.1 --status released --metadata ./metadata.json
```

Метаданные — JSON-объект со строковыми значениями, например `examples/metadata.json`. Они публичны для всех читателей приватного репозитория; не включайте секреты. `released` не подтверждает материал, допуски, раскрой, режимы оборудования или согласование производства.

Каждая версия — отдельный GitHub Release, тег `macstand/v1.0.0`, вложения `package.zip` и `nodi-manifest.json`. Такой тег допустим в Git; слеш — часть имени тега, а не готовый каталог GitHub. Nodi индексирует теги вместе с манифестами. [Ограничения имён Git](https://git-scm.com/docs/git-check-ref-format), [Releases API](https://docs.github.com/en/rest/releases/releases).

Сначала создаётся `draft=true`, загружаются ZIP и JSON. Только после загрузок для `released` отправляется обновление `draft=false, prerelease=false`. Для Nodi draft остаётся `draft=true, prerelease=true`, а в JSON явно записан `status=draft`; prerelease сам по себе не обозначает производственную готовность. Черновик не доступен через `get`. Для выпуска после черновика публикуйте новую версию: автоматического продвижения/замены существующего релиза нет.

При ошибке загрузки черновик сохраняется для проверки на GitHub. Повторная публикация той же версии отклоняется. Если ошибка произошла при финальном обновлении статуса, результат может быть неопределён из-за потери ответа: сначала проверьте релиз на GitHub. Удаление/исправление черновика выполняется вручную; Nodi не удаляет удалённые данные. Манифесты с несогласованным статусом или отсутствующими файлами отклоняются.

## Целостность и ограничения

- Только HTTPS; загрузки с API могут переходить на HTTPS CDN, без пересылки токена. Nodi проверяет приватность репозитория перед чтением/публикацией.
- ZIP до 256 MiB, суммарная распаковка до 512 MiB, до 10 000 файлов; JSON до 4 MiB. Это ограничения Nodi; GitHub допускает release asset менее 2 GiB. [Ограничения GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).
- SHA-256 ZIP и каждого файла, размеры и состав проверяются до установки результата. Распаковка идёт в временную папку; неверные файлы не становятся результатом.
- Запрещены абсолютные пути, `..`, обратные слеши, потоки NTFS, системные имена, ссылки, дубли и различия путей только регистром. Существующая целевая папка не заменяется. Локальный злоумышленник с доступом к переименованию родительских папок во время операции не входит в модель защиты MVP.
- Транспорт не предоставляет цифровую подпись пакета. SHA-256 защищает целостность относительно манифеста; редактор репозитория может изменить и архив, и манифест. GitHub на стороне сервиса не превращается Nodi в неизменяемое хранилище.
- Нет фоновой синхронизации, самостоятельного автообновления CLI, resume-download, retry публикаций, работы с оборудованием или CAD. Сборки macOS не подписаны/notarized. Обновления программой управляются Homebrew/winget; статус включения в официальный winget указан отдельно.

## Обновление и удаление

Обновление: повторно запустите установщик с новым проверенным комплектом или доверенным релизом. Скачанные проекты и конфигурация сохраняются. Убедитесь, что выполняющийся `nodi.exe` завершён.

Windows: удалите `%LOCALAPPDATA%\Nodi\bin\nodi.exe` и эту запись пользовательского PATH. macOS: удалите `~/.local/bin/nodi`; строку PATH из `~/.zprofile` удаляйте, только если она не нужна другим программам. При необходимости выполните `nodi auth logout` до удаления. Проекты и конфигурация не удаляются установщиком автоматически.

## Разработка и проверки

Нужен Go 1.27.2. Зависимостей вне стандартной библиотеки нет.

```powershell
go test -cover ./...
go vet ./...
.\scripts\build.ps1
```

Для локального компилятора этой рабочей папки:

```powershell
.\.tools\go\bin\go.exe test -cover ./...
.\scripts\build.ps1 -Go "$PWD\.tools\go\bin\go.exe"
```

Флаги сборки: `CGO_ENABLED=0`, `-trimpath`, `-buildvcs=false`, пустой build ID, версия CLI из стабильного тега. Порядок файлов ZIP и время в ZIP фиксированы; манифест инженерного пакета содержит реальное время подготовки. GitHub Actions собирает три бинарника, запускает Go-проверки и точные release-бинарники на Windows, macOS ARM64 и Intel, затем публикует релиз только по тегу `vMAJOR.MINOR.PATCH`. Вложения сначала загружаются в draft; стабильный релиз открывается после подтверждённых native-проверок и `winget validate`. Существующие релизы не заменяются. Для локального `-race` нужен совместимый C-компилятор; CI запускает race-проверки на macOS.

```powershell
go test -v ./internal/cli -run TestMockEndToEnd
```

Это явно **mock end-to-end**: реальные CLI-команды, упаковка, GitHub-совместимый HTTPS API, статусы, скачивание, SHA-256, сохранение локального пути, вызов подменённого opener и отказ от перезаписи. Используются фиктивные `examples/manufacturing/*.dxf` и `*.pdf`, помеченные `NOT FOR MANUFACTURING`. Они не прошли инженерную проверку.

Первоначальная mock-проверка — в [docs/VALIDATION.md](docs/VALIDATION.md); реальные результаты GitHub, Homebrew и winget — в [docs/NODI-02-STATUS.md](docs/NODI-02-STATUS.md). Реальные GitHub credentials не включены в исходники или релизы. Для проверки передачи доступны фиктивные пакеты `nodi-demo` и manually dispatched workflow в приватном хранилище: автор получает `Contents: write`, получатели — отдельные токены `Contents: read`. На предприятии нужно разрешение ответственных за оборудование и информационную безопасность.

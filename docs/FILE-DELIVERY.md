# Исправление доставки файлов после Nodi 0.2.1

Дата: 2026-10-11. Новая версия Nodi ещё не опубликована.

## Аудит и минимальные изменения

Реальный GitHub API подтвердил для `macstend3d/v0.1.0` (release 409792032): draft=false, prerelease=true, manifest schema 1 status=draft. В 0.2.1 автоматический publish создавал draft; ручное снятие GitHub draft не обновляло manifest. Проверка согласованности закономерно отказывала. Кроме этого, обычная публикация требовала два подтверждения, упаковщик принимал только инженерные форматы.

Сохранены Go, CLI, стандартная библиотека, GitHub Releases, schema 1, отдельные read/write credentials, SHA-256, версии и атомарное резервирование Git ref. Интерфейс storage.Store дополнен чтением версий выбранного проекта, чтобы повреждённый чужой релиз не блокировал info/get. Команды остаются отделены от GitHub-моделей. Нет новых серверов, БД, зависимостей, фоновых процессов и провайдеров.

Минимальный план выполнен: общий путь отправки для send/publish, default released, --draft, проверка загруженных байтов и конечного состояния, setup доступа, переиспользование NODI-04 через setup --completion, политика файлов из README.

## Поведение

В reliability candidate A2 прерванная собственная публикация восстанавливается повтором той же `send`/`publish` команды. Подготовленный ZIP и journal сохраняются в Nodi config directory; уже подтверждённый удалённый результат автоматически согласуется с локальной версией без новой публикации. При неизвестном ownership, повреждённом journal или изменениях неполного source/remote операция сохраняется и отвергается. Новых команд нет; подробные границы и RED/GREEN — в [A2/B02](NODI-RELIABILITY-A2-B02.md). Публичная 0.4.1 этим документом не объявляется обновлённой.

- `send PATH`: файл/каталог, basename определяет имя; точная привязка сохраняет project/repository/metadata. Нет обычных подтверждений и записи в непривязанный источник. Частичная отправка привязанного проекта отклоняется.
- `publish`: привязанный проект, released по умолчанию. --draft / --status draft явно запрашивают черновик. Старый явный publish PROJECT PATH --version X.Y.Z сохранён.
- Неизменённый released не создаёт версии. Неизменённый draft при запросе released получает новую версию с сохранением старых assets.
- ZIP детерминирован, schema 1 не изменена. Обычные файлы любых форматов включаются; скрытые/credential/key/service имена и конфигурация Nodi исключаются. Политика имён и её ограничения описаны в README.
- До финализации скачиваются ZIP/manifest: сравниваются поля, размер и SHA-256. После PATCH читаются release по тегу и assets. Ответ PATCH сам по себе не означает успешную публикацию.
- `get`: latest/--version, Desktop/Nodi/PROJECT/VERSION. Любой существующий destination отклоняется; пользовательские файлы сохраняются, повторную копию можно получить через другой --output.
- `setup`: private storage, saved credentials, скрытый ввод недостающего токена, сохранение через прежние DPAPI/0600 механизмы. Write endpoint проверяется заведомо недопустимым Git ref: 403 означает отказ, 422 означает достижение валидации; объект не создаётся. Реальная публикация всё равно проверяет каждую операцию. --check выполняет только GET и не записывает config/credentials. Read-слот с write-правами отмечается отдельно.
- NODI-04 не дублируется: прежняя реализация consent/backup/BOM/UTF-16 используется через `setup --completion [--check]`. Установщики определяют поддержку нового флага по help и поддерживают старые binaries.

## Безопасное восстановление macstend3d

Исходные assets скачаны без изменения release:

- Manifest asset 631258100, SHA-256 `954315384399894cb9095638b3034367b0d4555383eb5ea6349a67ff164de2ec`.
- ZIP asset 631258072, 825627 байт, SHA-256 `41f347e7d47ce14106283fed174549a8999b65acccabf3ca7c198655dc176345`.
- Проверены состав ZIP и SHA-256 всех шести файлов. Технологическая пригодность не проверялась.

Manifest не подписан, но GitHub asset digest хеширует его целиком: изменение status изменит байты и digest. Проверка статуса не ослаблена. Безопасный путь — новая версия `macstend3d/v0.1.1`: тот же ZIP побайтно, новые version/status/published_at в новом manifest, новая атомарная публикация и проверка конечного состояния. Старая 0.1.0 остаётся свидетельством сбоя. In-place замена manifest/flags не предлагается.

Подготовлены `.tools/transfer-audit/recovery-manifest.json`, исходный package.zip и проверенная распаковка original-verified. Восстановление ждёт отдельного подтверждения пользователя; существующий релиз не изменён.

## Проверки

Локальные Go-тесты и go vet: PASS. TLS mock E2E: send шести файлов, кириллица/пробелы, latest/history, unchanged без POST/PATCH, default released/explicit draft, SHA-256 и фильтр файлов. Дополнительно проверены 401/403/404/422/429/500, отсутствие сети, неполная загрузка, конкурентное резервирование версии, изменение source/remote во время подготовки, ложный PATCH, неудачный final GET, повреждённый uploaded ZIP и отказ от перезаписи. Setup проверяет сохранение только валидированных credentials, отсутствие токенов в выводе, read-only --check. Старые schema-1 пакеты принимаются с прежними строгими проверками.

Реальные GitHub API, Windows: PASS для `nodi-transfer-20261011173919/v0.1.0` и `/v0.1.1`. Шесть файлов из пути с пробелами/кириллицей; flags draft/prerelease=false/false; изменён один файл; latest и старая версия получены; повторный send сохранил release ID/updated_at. Сохранённый здесь read-слот фактически допускает запись: локальный прогон не доказывает read-only роль. Токены пользователя не заменялись и не переносились в CI.

- Тестовый проект `nodi-delivery-38161472625-1`: версии 0.1.0 и 0.1.1 опубликованы; изменён один файл; неизменённый send не создал 0.1.2. - На каждом получателе также успешно получен старый `nodi-ux-1/0.1.1`: реальная совместимость прежнего schema 1. Существующие старые packages не заменялись.

Это исправлено чтением выбранного проекта, без ослабления его проверок. Повторный запуск выше успешен; свидетельства первого запуска сохранены.

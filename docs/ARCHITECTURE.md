# Nodi: контракт

`cmd/nodi` создаёт CLI и контекст отмены. `internal/cli` разбирает аргументы и вызывает интерфейс `storage.Store`. `internal/storage` реализует GitHub Releases через HTTPS. `internal/archive` создаёт и проверяет ограниченный ZIP. `internal/local` определяет Desktop, открывает папки и хранит JSON-записи скачиваний. `internal/config` хранит настройки и отдельные credentials. `internal/model` задаёт идентификаторы и манифест. Замена backend требует новой реализации `Store`; команды не зависят от GitHub-структур.

Манифест schema 1:

```json
{
  "schema": 1,
  "project": "macstand",
  "version": "1.0.0",
  "description": "Manufacturing exports",
  "status": "released",
  "published_at": "2026-10-11T00:00:00Z",
  "archive_sha256": "<64 lowercase hex characters>",
  "archive_size": 1234,
  "files": [
    {"path": "drawings/plate.dxf", "size": 123, "sha256": "<64 lowercase hex characters>"}
  ],
  "metadata": {"material": "operator supplied"}
}
```

SHA-256 ZIP находится во внешнем JSON, не внутри ZIP, поэтому нет циклического хэширования. SHA-256 файлов рассчитывается из тех же байтов, которые записываются в ZIP. JSON, размеры, состав ZIP, типы записей, пути, коллизии и хэши проверяются перед установкой результата. Все файлы из манифеста обязательны; лишние записи запрещены. Пакет не включает конфигурационные файлы или исходный JSON с дополнительными metadata.

Теги: `PROJECT/vMAJOR.MINOR.PATCH`. На чтение индексируется только согласованный тег + schema 1 + оба assets. Не используется глобальный GitHub `latest`, поскольку репозиторий содержит несколько проектов. Последняя версия определяется числовым сравнением SemVer core. `published_at` — UTC-время подготовки публикации, а не подтверждение завершения транзакции API.

Публикация проверяет существующие релизы, включая drafts, и существующий Git tag. Затем новый draft получает assets; Nodi скачивает manifest и ZIP для сверки полей, размера и SHA-256 до финализации. Финальное обновление относится только к созданному ID; после него проверяются release по тегу и байты assets. Опубликованные версии не перезаписываются командами Nodi. GitHub API при конкурентных действиях остаётся источником окончательного результата; процесс не реализует глобальный распределённый lock. Ошибка не запускает автоматический retry и не удаляет свидетельства неудачной публикации.

Токены находятся в отдельных read/write слотах. Для `list --all` / `info --all` нужен write-слот из-за правил доступа GitHub к drafts. CLI не принимает token-флаги, не выводит тело ошибок GitHub или сетевые ошибки с URL/credentials. При asset redirect заголовок Authorization удаляется; HTTP downgrade запрещён. Проверка приватности происходит перед операциями. Файл с хэшами не является независимой подписью издателя.

Установщик и `dist` относятся к распространению самой программы. GitHub storage репозиторий относится только к инженерным пакетам. Код, CI и fixtures можно хранить в локальном/отдельном Git-репозитории `nodi`.

NODI-06 сохраняет `Store` и добавляет отдельный интерфейс `storage.Deleter`: read-only план и выполнение подтверждённого снимка. GitHub release ID, проверка tag SHA, порядок Release → tag, tombstones и HTTP находятся в provider. CLI отвечает за аргументы, таблицу и ввод подтверждения. Проверка обновления самой CLI также отделена от приватного package storage; public GET не передаёт пользовательские credentials.

История удалённых номеров — постоянные refs `refs/tags/nodi-deleted/PROJECT/vVERSION` на тот же commit SHA, что исходный package tag. Они создаются и проверяются до удаления Release; Nodi не удаляет и не переписывает их. `State` учитывает их в максимальной версии, `Publish` запрещает номера не выше исторического максимума. В list/info/completion эти refs не показываются. Неполный релиз, неподтверждённый tag или оставшийся reserved tag требуют отдельного разбора; автоматического восстановления нет. Сбой после удаления Release сохраняет tombstone и сообщает состояние Release/tag; это не транзакция. Владельцы write-доступа GitHub по-прежнему могут вручную изменить refs, поэтому граница доверия — доступ на запись в storage repository.

Замена GitHub будущим объектным хранилищем имеет **среднюю сложность**. ZIP, schema 1, SHA-256, загрузки и большинство CLI можно сохранить. Новый provider должен реализовать индекс проектов, статусы, резервирование версий, неизменность объектов, историю удаления и проверяемые частичные сбои. Семантику Git refs/Release staging потребуется заменить условными записями или другим механизмом конкуренции. Один HTTP-адаптер не обеспечит эти гарантии. Сейчас другие backend не добавлены, масштабного рефакторинга нет.
